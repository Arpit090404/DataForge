## 3. Resize and positioning detail

There is no React pointer-resize handler, `ResizeObserver`, width persistence, or local storage for panes in the current shell. The left aside has CSS `resize:horizontal` with 210–340 px bounds; the grid stays 248 px. Threads uses CSS `resize:vertical`, initially 33% with 165 px minimum and 58% maximum. The inspector has a fixed 270 px grid track and no resize control. Notebook uses a separate fixed 248 px left track, changing to 210 px under 850 px, and removes the track when its sidebar is closed (`styles.css:111-113,190`). A future width implementation must clamp restored values after viewport changes and avoid storing a width that starves the centre.

The existing centre `minmax(0,1fr)`, `min-width:0`, auto margins, and Notebook max-width rules are useful. The defect is the disagreement between CSS-resized box and grid track, plus mode placement within a track that moves relative to the whole window. A sidebar's width change should reflow the central track immediately. A readable content column should stay centred between the **current** sidebars, including asymmetric inspector/open states.

## 4. Window integration and risks

`apps/desktop/src-tauri/capabilities/default.json:5-6` grants the main window `core:default` and `dialog:default`. No window-specific capability is declared. Installed `@tauri-apps/api/window` exposes `minimize`, `maximize`, `unmaximize`, `toggleMaximize`, `close`, `isMaximized`, `startDragging`, and `startResizeDragging`; its local type documentation explicitly requires `core:window:allow-start-dragging` for `startDragging`. Verify the individual permissions needed by every selected operation against the installed Tauri schema before implementation. `setTitleBarStyle` is documented as macOS-only and is not the Windows solution.

`App.tsx:95-99` installs a `beforeunload` warning for dirty Notebook state. A custom Close action must preserve or deliberately replace that protection, including project-switch and save failure behavior; direct native close could bypass the expected prompt. WebView drag regions must exclude buttons, menus, text selection, and input fields. Frameless Windows behavior can differ across WebView2, scaling, maximized state, multiple monitors, and Snap. There is no tested custom-chrome guarantee today.

The fixed top-centre switcher and custom controls compete for horizontal space. At the 900 px minimum, constrain project text, hide secondary labels or move project actions into an existing menu pattern before allowing overlap. The right inspector CSS breakpoint currently hides without reconciling `inspectorOpen`; state and visual behavior must agree. Native rendering and interaction are required to validate these choices.

## 5. Target architecture and implementation order

1. **Shell geometry** — React owns bounded sidebar widths; CSS grid consumes those widths; full-height edge handle and keyboard control resize the left panel. Keep central content centred inside the remaining track. Define responsive collapse and persistence semantics in the design system. *(React component, CSS/layout, design-token.)*
2. **Top navigation** — Move the mode group to one shell-level fixed centre position; remove the workspace inspector toggle; reconcile topbar project identity and inspector state at narrow widths. *(React component, CSS/layout.)*
3. **Window chrome proof** — Implement caption actions and minimal Tauri permissions, verify drag/double-click/close/resize/Snap/DPI natively, then disable decorations. Do not ship the frameless switch before those checks pass. *(Tauri/Rust integration, React component, CSS/layout.)*
4. **Shared control and font pass** — Convert standard contextual buttons to shared sizes, record justified compact exceptions, package and test JetBrainsMono Nerd Font, update `DESIGN_SYSTEM.md`. *(Design-token, React component, frontend assets/config, CSS/layout.)*
5. **Notebook refinement** — Apply spacing and control rules to existing Home/Editor; verify keyboard and narrow-window states without changing execution or storage. *(CSS/layout, limited React component.)*
6. **Chat presentation, then Dashboard** — Add role-specific conversation/results only when backed by real agent/investigation state; apply shell and inspector rules to Dashboard when implemented. *(Future React component, CSS/layout.)*

## 6. Decisions and verification before implementation

No user decision blocks the audit. The redesign target chooses a whole-window fixed top-centre mode group and a packaged Nerd Font for technical text. During implementation, confirm the exact font asset/license, width persistence policy (global versus per-project), and whether the right inspector also becomes resizable in the first shell pass; these are implementation choices, not claims of current behavior. Native Windows screenshots were not available in the repository inspection. No builds or tests were run for this documentation-only audit.
