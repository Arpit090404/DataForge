# Worker fencing and Windows process supervision feasibility

**Status:** Experiment report, 2026-11-13. ADR 0009 remains proposed. This report does not approve Milestone 1.

## Verdict and environment

**Failed as a complete old-worker fencing boundary; the direct parent/child mechanism is partially proven.** The isolated [harness](../experiments/worker-fencing/README.md) passed 18/18 final assertions on one Windows installation, but documented out-of-job process creation prevents a claim that every possible old worker descendant is fenced. The registry reported `CoreSingleLanguage`, display version `26H2`, build `26300.9974`; its legacy product-name value reported “Windows 10 Home Single Language,” so the exact marketing edition is not established by that value. The harness used .NET SDK 10.0.301, Python 3.12.12, and embedded DuckDB 1.4.2. No other Windows build, edition, architecture, or host containment policy was tested.

The selected mechanism is a host-owned, unnamed Windows Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and no breakaway limits. The host starts the worker suspended, assigns it to the job, checks membership, durably writes a session/host/worker identity record, then resumes it. It creates the worker with handle inheritance disabled and a minimal environment. The worker's direct children inherit job membership. The host owns the only intended Job handle; if it dies, closing the last handle should terminate all job members. This is process-lifetime supervision, **not** filesystem, network, credential, or code isolation. [Microsoft's Job Object documentation](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) describes the close behavior and child-job behavior; [nested jobs](https://learn.microsoft.com/windows/win32/procthread/nested-jobs) began in Windows 8/Server 2012. The experiment's .NET 10 host has a narrower [supported Windows matrix](https://learn.microsoft.com/dotnet/core/install/windows); this spike does not select DataForge's minimum supported OS. A production Rust implementation needs its own compatibility proof.

## Ownership and recovery protocol proposed for ADR 0009

Use a unique host session ID, worker ID (PID plus process creation time), monotonically advanced worker generation, and durable operation ID. A host that owns mutable DuckDB representations must hold an exclusive project writer lease for the whole worker/recovery lifecycle. The host creates each worker suspended, attaches it to a non-breakaway, kill-on-close job, verifies membership, persists the session and worker identity, then resumes it. The job handle stays private to the host. Side-effecting IPC carries session, generation, request, and operation IDs; the host accepts responses only for a pending request in the current session/generation and records one terminal transition. Those IDs reject stale messages; **they cannot stop a live old DuckDB connection from writing**.

On clean shutdown, stop dispatch, request cancellation, terminate/wait for workers and descendants if needed, release the Job only after they are unable to mutate, then release the project writer lease. On restart: (1) acquire exclusive project ownership without breaking a live owner's lease; (2) load the prior ownership record; (3) establish that the old host and all supervised processes are terminated, using OS process handles and creation-time identity, and fail closed on ambiguous identity; (4) verify exclusive write access to mutable DuckDB state and app-owned artifacts; (5) advance generation and reconcile the operation journal; (6) only then start/enable new worker operations. No timeout or heartbeat authorizes step 5. Missing/corrupt ownership evidence, an inaccessible process, job-attachment failure, or unavailable exclusive storage access blocks recovery. This ordering is a **proposed contract**, not a production implementation or a fully proven guarantee.

The experiment's `recover` command waits on the recorded host, worker, and descendant identities, then successfully opens the synthetic DuckDB database read-write before emitting `recovery_start`. It does not acquire and hold a project-wide exclusive writer lease, enumerate all job descendants, or test simultaneous replacement hosts. Its ownership file is a single flushed file rather than a fully crash-safe journal. Thus it tests key steps of the protocol but does not establish the complete contract.

## Adversarial results

The final run's raw per-case identities, timestamps, rows, errors, and events are in ignored `experiments/worker-fencing/results.json`; the harness recreates them. Earlier development runs exposed harness observation errors (reading DuckDB while a writer held it, reading an ownership file during replacement, and treating a numeric handle collision as inheritance); those assertions were corrected before the final run. They were not product failures.

| Case | Observed result |
| --- | --- |
| Clean lifecycle | Host exited 0; worker exited; recovery began after exit; three synthetic rows remained. |
| Abrupt host termination | Host was terminated with exit code 1; worker exit was observed by OS process handle; row count stayed stable after exit. |
| Immediate restart race | Replacement recovery was pending while old host lived; after host termination and worker exit, `recovery_start` followed. Seven rows were present, showing old work continued **before** termination, as expected. |
| Direct descendant | Child was confirmed in the selected Job Object, then exited on host termination; its tick file stopped growing. |
| Breakaway flag | `CREATE_BREAKAWAY_FROM_JOB` was requested; the resulting child was still confirmed in the selected Job Object and exited. This tests that flag on this configuration only. |
| Repeated restart race | Ten descendant/restart trials passed; recovery started 268–383 ms after the host-kill timestamp (mean 300 ms). These are harness timings, not a delay used as a recovery gate or a reliability guarantee. |
| Missing or uncertain identity | Recovery returned codes 4 and 5 respectively and emitted no `recovery_start`. |
| Stale response | A small state-filter model rejected an old-session/generation response and a duplicate current response. Actual IPC transport and side-effecting duplicate delivery were **not** tested in this spike; see the prior [IPC/storage report](IPC_STORAGE_RECOVERY_FEASIBILITY_REPORT.md) for its separate partial proof. |

The raw report stores PIDs and process creation-time ticks for host, worker, and direct descendant; the OS wait establishes exit but a numeric worker exit code cannot be recovered after the crashed host's handles disappear. Timestamps are wall-clock observations, not a proof of filesystem flush ordering. The stable post-exit row count and child ticks support the mutation observation for these small fixtures only.

## Bypasses, limitations, and residual risks

- A Job Object does not restrict filesystem or network access. The trusted analytics worker still parses untrusted files; arbitrary generated Python remains deferred under [ADR 0008](DECISIONS/0008-python-execution.md).
- The job protects members only. [Microsoft explicitly documents](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) that children created through `Win32_Process.Create` are not associated with the job. A same-user broker or another out-of-job process-creation path could likewise leave a mutating process alive; a worker might also try to duplicate or retain the Job handle. These bypasses were not exercised locally. If any such process can mutate shared storage, last-handle closure cannot fence it. The direct-child results therefore do **not** prove the central requirement for arbitrary descendants.
- The harness verifies a recorded direct child, not a complete OS-enforced inventory of every descendant. A host crash before a child identity is recorded is not separately fault-injected. Job membership is expected to kill normal descendants, but complete descendant ownership is not proven.
- The experiment does not prove exclusive project ownership across two simultaneous new hosts. Opening DuckDB once is not an exclusive lease held through reconciliation; artifact mutations may use separate file handles. Concurrent reconciliation remains possible in the current harness.
- Process identity checks fail closed on a live PID with a mismatched creation time, but a missing process is treated as exited. The ownership record is not protected from a malicious same-user writer and is not an atomic, journaled write. Power loss and PID reuse at an unobserved boundary were not tested.
- Windows 8/Server 2012 is the earliest documented nested-Job capability, not a supported DataForge version decision. Only build `26300.9974` was exercised. Windows 10/11 editions, older builds, Windows Server, ARM64, elevated/unelevated combinations, existing parent jobs, and production packaging remain unproven. The .NET 10 test host itself is not the intended Rust host.
- Actual Rust–Python IPC stale messages, worker restart under a newly persisted generation, simultaneous hosts, storage lock failure during a live old worker, and repeated power-loss races remain untested here. The prior IPC experiment covered some protocol behavior separately, without this Job boundary.

## Recommendation and Milestone 1 implication

**Block the current recovery architecture from acceptance.** Keep ADR 0009 **proposed**. Its storage journal direction remains useful, but amend it before acceptance to require: a demonstrably exclusive project writer lease held through reconciliation; job attachment before worker execution; private Job-handle lifetime; a fail-closed durable ownership record; explicit session/generation/operation checks; and a verified way to exclude or prevent mutating processes outside the supervised job. Then test the production Rust supervisor with the actual supported Windows matrix and failure points, including simultaneous replacement hosts and brokered/escaped descendants. If those escapes cannot be excluded, redesign the storage writer boundary so the worker cannot directly mutate shared DuckDB or published artifacts.

Old-worker fencing is **failed for the full acceptance criterion** and **partially proven for direct job-member processes** on the tested build. The Milestone 1 recovery gate is **not satisfied**. Do not start Milestone 1 on this evidence alone.
