# Storage ownership boundary — proposed design

**Status:** Proposed for architecture review. No production implementation or security proof exists. This design responds to the failed full-boundary verdict in [the worker-fencing report](WORKER_FENCING_FEASIBILITY_REPORT.md). ADR 0009 remains proposed.

## Guarantee and threat boundary

Required guarantee: a process surviving an interrupted analytics execution cannot mutate authoritative project state or cause recovery to accept partially written data. A Job Object, PID list, session token, heartbeat, or journal record cannot enforce this against a process that still has a writable storage handle or can reopen the files. Treat a parser compromise as a malicious worker with all rights granted to its Windows security identity; treat a crash or delayed buffered write as an accidental failure. Unrelated malware already running with the host user's unrestricted identity, an elevated administrator, and a compromised host/storage broker are outside this worker-boundary guarantee. If an escaped worker can obtain that unrestricted identity, the guarantee fails and the design must be blocked.

Authoritative state means SQLite metadata/journal, DuckDB representations and WAL, committed artifacts, managed sources, their parent directories and names, and backups. Worker-owned scratch data is never authoritative. The host may use it only as untrusted input to a new, host-owned commit. An artifact's hash proves integrity only if a malicious worker cannot also alter the authoritative metadata or replace the file after validation.

## Candidate comparison

| Required property | A. Host-owned storage and brokered commits alone | B. Per-execution workspaces alone | C. Restricted worker identity and ACLs alone |
| --- | --- | --- | --- |
| 1. Authoritative ownership | Host owns SQLite, DuckDB and artifacts. | Host owns metadata; worker workspace is not authority until copied and committed. | ACL/token can reserve authority to a host identity, but does not define commit ownership. |
| 2. Worker permissions | IPC contract gives no write API, but an unrestricted same-user worker can still open project paths. | Worker writes scratch and, without OS denial, can also open authority. | Properly constrained token/ACL may deny authority writes; exact rights need proof. |
| 3. Surviving descendants | Old IPC responses are ignored, but an unrestricted out-of-job descendant can write by path. | Survivor can continue mutating scratch; this is safe only if scratch is never promoted directly. | Ordinary children retain restrictions; brokered out-of-job launch/token regain remains unproved. |
| 4. Open handles after host death | Any leaked writable project handle defeats the path-only rule. | A retained scratch handle can keep changing bytes after rename or while the host copies. | ACL changes do not revoke an already open writable handle; launch must prove none leaks. |
| 5. Output promotion | Host validates a complete stream, writes private staging, and uses same-volume no-replace promotion where proved. | Never rename a worker-writable file into authority; copy to private staging, then validate that copy. | Access control alone gives no atomic promotion; combine with host-owned staging. |
| 6. Recovery/orphans | Journal reconciles host-owned DuckDB/file candidates; preserve committed evidence. | Scratch is disposable only after checking references and live handles; cleanup races need proof. | Token denial prevents survivor writes but still requires journal/orphan reconciliation. |
| 7. Duplicate/retry | Host operation IDs and final SQLite transition suppress duplicate publication; uncertain non-idempotent work gets a new attempt. | Each retry uses a fresh workspace and attempt ID; old scratch never becomes current. | Access control does not suppress duplicate messages or side effects. |
| 8. Cross-store consistency | SQLite, DuckDB and files cannot commit atomically; final SQLite publication follows verification, with recovery for gaps. | Workspace isolation does not solve cross-store atomicity. | ACLs do not solve cross-store atomicity. |
| 9. Windows/privileges | Ordinary desktop privileges suffice, but same-user malicious-worker guarantee fails. | Ordinary privileges suffice; reparse/hard-link/rename behavior varies by filesystem. | AppContainer/restricted token may avoid admin privileges; Python packaging, ACLs, WMI and supported OS/filesystem behavior need proof. |
| 10. Cost/performance | Host-side DuckDB integration and streamed bulk data are material changes; benchmark throughput and memory. | More disk and copy I/O; large datasets may be expensive. | Token/ACL construction and packaging are complex; runtime overhead needs measurement. |

No candidate alone satisfies the full threat model. The recommended design combines **A with a tested C boundary**; an execution workspace may be used only as untrusted scratch, never as a promotable authority file. This preserves the accepted Python analytics direction in ADR 0002, but moves persistent DuckDB writes out of the Python analytics worker. If C cannot prevent an out-of-job process from regaining the host user's rights, use a genuinely separate storage security principal/service or conclude that the guarantee is unavailable on that configuration. A service is a fallback requiring separate product and privilege review, not silently approved here.

## Proposed host-owned commit boundary

1. The Rust host is the sole project writer and holds an OS-enforced, project-scoped exclusive ownership handle from open through reconciliation and normal operation. A second host blocks or opens read-only; it never steals a lock based on a timestamp. The exact Windows primitive, lock-file placement, and supported local filesystem must be proved. Host-owned storage code (in-process or a host-controlled trusted component) owns DuckDB; the Python analytics worker never opens `analytics.duckdb`, its WAL, SQLite, artifact directories, or managed sources for writing. No writable project handle is inherited or duplicated to it.
2. The host opens approved source files itself and gives the worker bounded input bytes/records through IPC or a read-only handle whose scope is proved. The worker receives opaque registration/representation IDs, never authoritative paths or credentials. For initial proof, use brokered bytes; direct source handles and high-throughput shared memory are optimization decisions requiring separate access proof. Original source files stay read-only.
3. The worker parses and computes using application-owned Python. It returns bounded schema/row/result chunks or artifact bytes over versioned, back-pressured IPC with session, generation, request, operation, chunk sequence, length and digest. The host validates types, schema, limits, sequence, completeness and final hash before committing. A worker pathname, hash claim, success response, or scratch file is never accepted as authority. Large-result transfer cost must be benchmarked; inability to stream a supported format within limits is a product-scope decision, not a reason to give worker project write access.
4. After committing an SQLite operation-journal `prepared` record, the host writes candidate DuckDB data under a new operation-scoped representation ID using a host-owned DuckDB connection/transaction. It writes artifact bytes to a private host-owned staging file with no worker access, flushes and closes it, validates hash/size/schema, and promotes to a never-overwritten name on the same supported volume. The host then commits the published representation/artifact references and terminal execution status in one SQLite transaction. There is **no atomic transaction across DuckDB, filesystem and SQLite**. A crash at any boundary leaves an unpublished candidate to reconcile, never an inferred success.
5. On restart, a replacement host first acquires exclusive project ownership. It does not need to prove that every old analytics process exited **only if** the OS access boundary proves those processes cannot write or reopen authoritative storage and the host never passed writable handles. It advances the worker generation, reconciles the journal with host-owned DuckDB/file inventory and hashes, preserves completed references, quarantines unreferenced outputs, and only then dispatches work. If access control or exclusive ownership is uncertain, recovery blocks. Old-session messages and duplicate chunks are ignored; they do not authorize publication. Retried non-idempotent work gets a new attempt after reconciliation.
6. Quarantine/cleanup is performed only by the owner after checking committed references and file identity. It is repeatable and recorded. Do not follow reparse points or accept a mutable worker path; detect replaced directories, symlinks, hard links, unexpected file IDs, or hash mismatches and block/flag the project. A promoted artifact is immutable by application policy, protected from the worker by OS access control, and checked again during recovery/read. The host/user can still intentionally modify a project file; that is outside worker isolation and must be detected rather than silently trusted.

The project directory layout can remain `project.sqlite`, `analytics.duckdb`, `sources/`, `artifacts/`, `staging/`, `backups/`. `staging/` becomes host-private; any worker scratch lives outside this authority tree. The host owns all names and directories. DuckDB materialization may need a host-side library/broker and a defined bulk-data contract; neither implementation nor a production dependency is added by this proposal. The prior IPC/storage spike used worker-owned DuckDB writes, so its pass results **do not validate this new boundary**.

## Windows enforcement and compatibility

The proposed proof target is an AppContainer worker with no broad filesystem/network capabilities, no access to the project tree, no writable handles, and brokered input/output. [Microsoft describes AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-for-legacy-applications-) as limiting a process and its usual children to granted resources, but unpackaged desktop/Python support is complicated and unverified here. A [restricted token](https://learn.microsoft.com/en-us/windows/win32/secauthz/restricted-tokens) with restricting SIDs and explicit ACLs is a candidate fallback; Windows performs two access checks, but correct ACLs, child/broker behavior and filesystem compatibility still require empirical proof. An ACL on a folder alone does not protect against a process with the same unrestricted user identity, existing handles, owner/DACL powers, or brokered launch under that identity. The [Job Object finding](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) specifically leaves `Win32_Process.Create` descendants outside the job. Job Objects remain useful for lifecycle/resource limits, not the storage security boundary.

Proof must cover the actual Windows version/edition/architecture, filesystem, packaging mode, Python/native libraries, WMI/COM/scheduled-task/brokered process creation, handle inheritance/duplication, reparse/hard-link attacks, ACL replacement, and concurrent hosts. If an AppContainer child or broker can regain an unrestricted user token and open the project, the design fails. Do not claim network isolation or access to unrelated user files is prevented until tested; the provider/agent boundary is separate.

## Decisions requiring review

- Choose the supported Windows and local filesystem matrix and whether network/removable/project-synced folders are excluded from the initial guarantee.
- Approve a host-owned DuckDB writer and bounded bulk IPC despite the performance/packaging change. Select the host-side DuckDB integration only after the spike; no dependency choice is made here.
- Choose AppContainer versus a restricted-token/ACL construction from empirical results; decide whether a separate security principal/service is acceptable if both fail.
- Define maximum streamed input/output sizes, backpressure, representation materialization limits, and behavior when a format exceeds them.
- Decide whether project tampering by unrelated same-user software is a supported adversary. If yes, an ordinary same-user desktop host cannot offer a strong anti-tamper guarantee without a separately protected authority.
