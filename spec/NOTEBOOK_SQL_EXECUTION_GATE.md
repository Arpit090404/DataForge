# Notebook SQL Code cell execution gate

**Status:** No-go for production SQL execution, 2026-11-24. No SQL Code cell execution is implemented. This document narrows the future slice under proposed ADRs 0005 and 0011; it does not approve general SQL.

## Current boundary

Notebook Code cells persist source and a `python` or `sql` language label, but have no run command or output association. The host accepts only `AnalyticsRequest` (`rows` or `group`), rejects unknown request fields, resolves a registered dataset ID, validates columns and operations, and compiles application-owned SQL with bound filter values. It does not accept SQL text. The host records each typed execution and pins a representation for Result replay; a successful rerun can retarget the same Result block in a transaction. These are working typed-analysis capabilities, not Code execution.

The existing analytical path caps input at 64 MiB and 250,000 CSV rows, pages at 1–200 rows and 1 MiB, offset at 100,000, and concurrency at one operation. DuckDB is configured for 256 MB buffer memory, 256 MB temporary storage, and two threads, with external access and extension autoload disabled. A 30-second timer requests interruption. Replay opens the representation read-only and checks its recorded engine/materializer versions. The initial materialization connection is writable. These controls do not establish a hard process memory, CPU, disk, wall-time, filesystem, or network boundary. Interruption is best effort and no worker can be forcibly terminated. Persistent DuckDB growth and cross-store recovery lack proved bounds.

## Minimum future SQL surface

The first SQL Code cell slice should accept one UTF-8 statement of bounded length (proposed maximum 8 KiB): a read-only `SELECT` over one host-resolved registered representation. Permit explicit column projections, literal/bound comparisons, boolean expressions, grouping, aggregates, ordering, and a bounded result page only after each construct and function has an audited AST policy. Exclude joins, CTEs, subqueries, windows, views, macros, table functions, external scans, arbitrary function names, and all other statement classes from this first slice. In particular reject multiple statements, DDL/DML, `COPY`, `ATTACH`, `INSTALL`, `LOAD`, `PRAGMA`, `SET`, and path or URL access. String matching, a leading `SELECT` check, or a textual `LIMIT` is not authorization. Resolve every relation and column through the host catalog; user SQL cannot supply a file path, physical table name, or trusted setup statement. Extend the surface only with separate adversarial tests and an explicit policy revision.

Use a query connection opened read-only against a pinned representation, with verified external-access and extension restrictions on the exact embedded DuckDB build. The host must wrap or otherwise enforce pagination and fetch incrementally, aborting at the row and byte caps. Start with the current 200-row/1-MiB page and single-operation concurrency caps; retain the 30-second deadline and 256-MB DuckDB settings as defense in depth, then establish OS-enforced memory, CPU, and scratch-disk limits before enabling SQL. Cancellation must first interrupt, then terminate the disposable execution process by a deadline, wait for confirmed exit, and reject late output. A request to cancel alone is not a completed cancellation.

Each submission must save the exact submitted SQL or a protected immutable source reference and hash, Code block ID and revision, policy/contract version, resolved dataset and representation IDs, source fingerprint, schema/materializer/engine versions, limits, timestamps, terminal status, and output scope. Do not log SQL or row values to diagnostic streams that may contain secrets. A successful execution may create a separate Result block referencing its new execution ID; a rerun creates another execution and may retarget that same Result block only after success. Keep Code edits independent of prior evidence. Replay must use the original policy and pinned representation or report unavailable, never silently reinterpret a stored query under a newer policy. The current execution schema (`schema_version=1`, typed `rows`/`group` parameters) and Result replay decoder cannot represent this contract; add a versioned SQL execution kind and replay path before wiring the UI.

## Blocking proof gates and smallest implementation sequence

1. Accept an ADR 0005/0011 amendment for this restricted SQL surface and its threat model. The present ADR 0005 explicitly excludes submitted SQL from Milestone 1. The DuckDB CLI 1.4.2 feasibility experiment is not proof for the embedded 1.4.5 Rust path.
2. Implement and adversarially test an AST/binder policy on the pinned embedded version, including nested syntax, unknown relations/functions, setting changes, external reads, and statement stacking. Prove that generated logical column names map only to the selected registered representation. Test source and representation hashes before and after rejected and accepted queries.
3. Run queries in a disposable, OS-confined process that cannot read unrelated files, reach the network, or write source/project stores. Prove process and descendant containment, hard memory/CPU/scratch limits, timeout termination, cancellation, crash recovery, and fail-closed startup on supported Windows builds. DuckDB settings and a subprocess alone are insufficient. Keep representation creation and authoritative writes host-owned.
4. Add a versioned execution record and bounded SQL replay/output path, with cell revision provenance and atomic Result retargeting. Test restart, changed/missing sources, unavailable representations, failed and cancelled reruns, and unchanged typed-analysis behavior before exposing a Run control on SQL Code cells. Python remains unavailable.

Until these gates pass, Code remains an editor and the existing built-in typed analysis form is the executable Notebook path. Do not route Code text through `run_analytics` or label a typed operation as SQL execution.

## Disposable Windows feasibility probe (2026-11-24)

`experiments/duckdb-rust-spike/sql-boundary-proof.cjs` drives a separate Rust executable using embedded DuckDB 1.4.5 and synthetic files only. A candidate parent-side AST allowlist parsed by the prior DuckDB 1.4.2 CLI passed 21 cases: approved single-table selects/aggregation succeeded; DML/DDL, `COPY`, `ATTACH`, extension commands, settings, stacked statements, external reads, unknown tables/functions, CTEs, subqueries, joins, and oversized input were rejected. This **does not prove the SQL policy** for 1.4.5. The embedded probe could not load the JSON SQL-serialization extension under its restricted configuration, so no same-version AST/binder policy was tested.

Direct probes against the 1.4.5 read-only, locked-config connection denied a synthetic unregistered file read, an HTTPS CSV read, `COPY`, `SET enable_external_access=true`, `LOAD httpfs`, and `INSTALL httpfs`. The worker reported `row_limit` above 200 rows and `byte_limit` above 1 MiB. Node's 150 ms timeout returned `ETIMEDOUT` for an expensive cross join; explicit cancellation observed the direct child exit with `SIGTERM`. A later query succeeded, and synthetic database/sentinel hashes were unchanged. These results are evidence for tested queries and settings, not proof of all SQL paths or Windows containment.

**Remaining blockers:** The child runs with the host user's filesystem/network rights; no AppContainer/restricted-token ACL or Job Object is applied. DuckDB's 128 MB memory and 32 MB temporary-storage settings are not hard OS limits; peak process memory, CPU, scratch disk, child descendants, and crash/restart recovery were not measured. Node killed one direct child, not a process tree. The 1.4.2 CLI AST may differ from embedded 1.4.5, and the probe's output conversion is experimental. No project catalog, execution record, provenance transaction, or committed Result was involved.

**Smallest production step after this proof:** Build a fail-closed same-version SQL parser/binder policy in an isolated proof harness, with only one approved representation and the restricted surface above. Pair it with a Windows process boundary that denies unrelated file/network access and proves hard termination plus resource limits. Only after those gates pass should the host add versioned SQL execution/replay records and a Code-cell Run control. The Rust host must continue to resolve/pin datasets, own project/DuckDB writes and result publication, and accept only bounded validated output from the disposable query worker.

## Windows OS isolation follow-up (2026-11-24)

**Candidate:** `experiments/duckdb-rust-spike/windows-isolation/` launches the same Rust/DuckDB 1.4.5 worker in a new AppContainer with no capabilities. The harness grants that package SID read access to its executable and one copied synthetic representation, grants a separate scratch directory write access, and gives no package-SID grant to a synthetic project file. It creates the process suspended, assigns a non-breakaway Job Object with kill-on-close, two active processes, 128 MiB per-process commit and 192 MiB job commit limits, then resumes. The host retains fixture creation, ACL setup, Job/profile handles, termination, and result-file ownership. No DataForge project or production path is used. Microsoft documents the [AppContainer launch attribute](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer) and [Job Object limit semantics](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects); these local observations are narrower than those platform contracts.

**Observed on one Windows x64 build** (`10.0.26300.9974`, display version `26H2`, registry edition `CoreSingleLanguage`; .NET SDK 10.0.301): 17 asserted cases passed. The AppContainer read the approved file, opened the copied DuckDB database read-only, and ran a fixed `COUNT(*)` query. Its reads/writes of the synthetic project file and write to the approved database failed; both file hashes stayed unchanged. It could not connect to a live loopback listener, while the same binary outside AppContainer connected. A 256 MiB committed allocation failed under the Job's 128 MiB process limit but succeeded in the same AppContainer without memory limits and outside it. A normal self-spawned child was confirmed in the Job and exited after the Job handle closed. A `CREATE_BREAKAWAY_FROM_JOB` self-spawn failed. The host's wall timeout and explicit cancellation each called `TerminateJobObject` and observed the worker exit. A continuous allocation loop terminated without timing out (`0xC0000409`); that exit alone is not used as proof of the exact memory cap. The unique AppContainer profile deletion returned success. Early sandbox runs failed to create the profile (`0x80070002`); after running with profile access, a minimal environment without profile variables caused `CreateProcessW` error 203. Those harness setup failures were corrected before the reported matrix.

**Limits:** A denied loopback connection on this build does not prove all network paths are blocked. Only a direct child and one breakaway flag were exercised; WMI/COM/brokered or injected out-of-job processes, inherited writable handles, reparse/hard-link attacks, and profile/SID ACL races remain untested. The Job has no CPU or disk quota; scratch usage, DuckDB spill, resource peaks, simultaneous hosts, host-crash recovery, and a real committed Result were not tested. AppContainer compatibility was checked with one read-only DuckDB query, not the whole permitted SQL surface or all supported Windows configurations. The earlier 1.4.2/1.4.5 parser mismatch also remains.

**Recommendation: no-go for Notebook SQL execution.** This candidate is feasible on the tested build for approved read-only DuckDB access and the direct Job/resource cases above. The next smallest proof is a synthetic out-of-job survivor and retained-handle attack against host-owned project stores, plus measured scratch/CPU limits and the supported Windows matrix. A same-version SQL policy and versioned host provenance/result contract are still separate gates. Keep SQL Code cells inert until those proofs and ADR approval are complete.
