# Rust–Python IPC protocol

**Status:** Proposed contract for architecture review; no implementation or conformance proof exists. Owner: Rust host. Peer: supervised trusted Python analytics worker. Arbitrary Python never runs through this worker.

## Transport and framing

One child process, stdin/stdout pipes, no listener. Each frame is a 4-byte unsigned big-endian byte length followed by that many UTF-8 JSON bytes. Reject zero length, malformed JSON/UTF-8, duplicate object keys, and frames above a configured hard cap (initial proof target: 1 MiB). Stderr carries bounded, redacted diagnostics only. The host limits buffered bytes and never waits synchronously on the UI thread.

On start, the worker sends `hello` with supported major/minor versions and capabilities. Host selects a compatible version or terminates it. Major mismatch fails closed; optional minor fields are ignored only when explicitly documented. Every envelope has `version`, `kind`, `request_id` (UUID for request/response/cancel), `host_session_id`, `worker_generation`, and `payload`; side-effecting requests also carry `operation_id` and `idempotency_key`. Responses carry `ok` or `error` with stable code, safe message, retryability, and optional diagnostic ID. No secrets or raw dataset rows in errors. The additional session field is a proposed contract change requiring conformance proof.

## Operations and authorization

Rust validates project/investigation/dataset IDs and permissions before dispatch. Worker validates message shapes and resolves only host-created catalog IDs. Initial user operations remain inspect schema, bounded preview, explicit representation materialization/refresh, and application-defined versioned analytical templates against a pinned representation. The host reads sources and executes DuckDB template/materialization writes; the worker performs only the required parsing/statistical computation on brokered inputs and returns bounded values. Registration and source-version decisions remain host-owned. No caller-supplied SQL text, identifiers, path, or arbitrary Python operation. Unknown operations return `unsupported_capability` without side effects. Worker output uses bounded, sequenced, back-pressured chunks with per-chunk length/hash and a final length/hash/schema manifest, all tied to session/request/operation IDs; Rust validates a complete stream and writes private staging. A worker-supplied path or file reference is never promotable. Exact chunk framing and limits require the storage-ownership spike before this contract is accepted.

## Lifecycle

Request IDs correlate out-of-order responses. Every side-effecting request carries a durable operation ID and idempotency key assigned by Rust before dispatch; the host owns output names and the worker must not publish metadata. Repeating an operation ID is permitted only when reconciliation has established that the operation is retryable and its prior effects are known; otherwise start a new attempt after user-visible interruption. `cancel` references the original request ID and receives an acknowledgement, but completion may race. Rust records the terminal result once. Each request has a deadline; on expiry, ask the worker to cancel, then terminate its process tree after a bounded grace period and mark the execution interrupted/uncertain. Do not equate a timeout or broken pipe with proof that no side effect occurred. On restart, first acquire exclusive project ownership and verify old workers cannot write authority; then advance generation, reconcile host-owned storage, and handshake before accepting new work. Job termination alone is insufficient for this gate. A response or chunk from an old session/generation, unknown operation, or terminal request is ignored and cannot publish output. Limit concurrent work initially to one execution per worker until measured and tested.

## Conformance proof

Round-trip and fault tests: partial/truncated frames and chunks, oversized payload, duplicate/missing/out-of-order chunks, digest/length mismatch, backpressure, duplicate/unknown IDs, out-of-order and late responses across sessions/generations, malformed fields, protocol mismatch, cancellation races, blocked worker, worker crash at every journal/output phase, disk full, and stderr flooding. Verify no worker path is accepted, orphan quarantine/cleanup is repeatable, and no duplicate artifact is published. See `STORAGE_OWNERSHIP_SPIKE_PLAN.md`.
