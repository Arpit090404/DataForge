# ADR 0011: Notebook execution through the Rust host

- Status: Proposed for review.
- Date: 2026-11-23

## Named registered dataset amendment (2026-11-27)

For deliberate local-user Code runs, the Rust host now resolves multiple registered datasets by name or stable dataset-derived handle. SQL uses query-local relations over pinned on-demand representations in the disposable read-only child. The execution records all bound dataset identities, fingerprints, representation IDs, and engine versions; those bindings are conservative context, not proven exact SQL lineage. Case-insensitive duplicate display names require stable handles. The Python bridge requests syntactically named datasets from the host before executing a cell and receives bounded typed values. Python inputs over 200 rows or the byte/combined transfer limits fail rather than silently becoming previews. A truncated saved SQL output is rejected as a complete Python input. This extends the trusted local-user path only; the autonomous-agent and OS-isolation gates remain unchanged. No Data Explorer or Python result publication is implemented by this amendment.

## Named result registry amendment (2026-11-27)

Successful SQL Code runs publish a named result only when their entire output fits the existing 200-row, 1 MiB result bound. The user may set a readable case-insensitive name; otherwise the host derives a stable name from the cell UUID. Larger outputs remain explicitly bounded previews and never become analytical inputs. A Python Code cell may explicitly stage up to four complete Pandas DataFrames with `dataforge.publish(name, frame)`; the host validates and commits them as named results after a successful execution. A later SQL or Python cell can reference a current name or the immutable `result_<UUID>` handle. Result IDs are independent of cell order and execution IDs. Rerunning under the same name retires the prior alias but retains its stable handle and payload until explicit release. Releasing a result tombstones its alias and payload reference; storage cleanup reclaims bytes only when no Code output or named result references the blob. The host stores publication metadata, output hashes, and input IDs in project SQLite. Source changes and retired aliases mark historical results stale, while their saved bytes remain usable as snapshots until release. Python kernel state remains outside this registry and cannot be reconstructed from it. SQL result payloads reuse existing saved Code output blobs; Python publications use the same blob table. This amendment does not change the trusted local-user security boundary or authorize agent execution.

## Python discovery and editor refinement (2026-11-26)

The Rust host enumerates Python candidates from PATH, the Windows `py -0p` launcher, and the existing optional uv listing. It verifies each candidate can start and import `ipykernel` and `jupyter_client` before the Notebook selects it. A remembered local interpreter is revalidated on startup; the manual override and file picker live in Notebook options. Missing dependencies produce actionable guidance, with no automatic installation. Changing the resolved interpreter still starts a different kernel on the next run and does not restore variables. The existing Code textarea now handles Enter indentation and Tab/Shift+Tab selection edits without changing the Jupyter protocol, execution records, output persistence, or Notebook execution shortcuts.

On Windows, discovery and validation subprocesses use `CREATE_NO_WINDOW`, like the active kernel bridge, so opening Notebook does not display transient console windows. Automatic discovery covers only its enumerated candidates; an existing compatible virtual environment outside those lists must be selected once through Notebook options. The selection is stored in WebView local storage under the stable project ID and revalidated on subsequent starts. An unavailable selection remains recorded until changed, so restoring that interpreter restores the choice. This is a machine-local preference, not portable project metadata.

## Manual output retention (2026-11-26)

Clear Output and Clear All Outputs remove saved-output associations for the chosen Code cell or notebook. Immutable execution records, submitted code, status, timing, and provenance remain in project history. A cleared SQL output can no longer be selected as a Python `sql_result()` input. Output bytes remain in the project until the user explicitly confirms storage cleanup. Cleanup runs in one immediate SQLite transaction, removes associations to deleted cells, and deletes only snapshot and image blobs with no live references; shared content-addressed artifacts remain. The UI reports project-wide saved and reclaimable bytes. No automatic deletion policy is applied.

## Manual execution controls (2026-11-26)

The Notebook toolbar runs the selected Code cell or all Code cells in document order, dispatching each through its existing SQL or Python host command. A single UI execution gate also covers typed analysis; Run All stops after a failed or interrupted cell and clears later queued indicators. Shift+Enter runs a Code cell then selects the next cell, while Text retains save-and-advance. Interrupt and restart operate on the active notebook's Jupyter kernel; the host reports stopped, running, idle, or unavailable status. SQL cancellation remains best effort through its existing execution ID. The toolbar's selected Python environment affects the next Python run; changing it starts a different kernel on that run and does not restore prior variables. Each Code run still creates its own immutable execution and bounded persisted output. This orchestration adds no agent execution or isolation claim.

## Trusted local Python amendment (2026-11-25)

An explicit Run on a saved Python Code cell may use an existing local environment with `ipykernel` and `jupyter_client`. DataForge discovers compatible executables on PATH or through an optional local uv listing; the user may select another existing executable with the file picker. The Rust host keeps one Jupyter kernel for the active notebook, owns execution records and accepts only bounded plain-text stream, result and exception messages from a versioned bridge. Variables persist until restart or notebook exit; execution counts identify order, not reproducibility. Interrupt uses Jupyter's kernel interrupt request; restart discards kernel state. The host and kernel run with the user's full local file and network privileges. Neither the protocol nor a subprocess is an OS sandbox. No agent may invoke this path, and no package installation is offered. SQL and typed analytical execution remain separate.

## Persisted Code output amendment (2026-11-25)

For explicit trusted Python and SQL runs, the host stores the validated bounded output against its immutable execution ID in project SQLite. A versioned snapshot references content-addressed blobs so repeated large image data is stored once. Reopening a notebook loads the latest saved output for each stable Code cell ID without executing code. The UI labels restored output and compares the exact recorded code with the current cell to mark stale output. Python kernel variables, imports and session state are never restored. Earlier executions and snapshots remain retained in project storage; the Notebook shows the latest output per cell. Output restoration does not promise reproducibility.

## Selected SQL–Python inputs (2026-11-26)

For explicit local-user Python runs, the host may attach one selected registered dataset and one selected successful SQL execution output. The host reads a bounded first page from its managed DuckDB representation or the saved SQL output snapshot, validates project ownership, and sends only typed columns, values, truncation and provenance through the existing Jupyter bridge. It records input IDs, fingerprints, representation IDs and engine versions with the Python execution. The kernel receives no database path or write handle through this API. `dataforge.dataset()` and `dataforge.sql_result()` return Pandas DataFrames with provenance in `df.attrs["dataforge"]`. A later run without selections clears the helper's previous inputs. This is a bounded snapshot, not a live table or full result transfer. The trusted kernel retains the user's normal OS privileges independently of this API. No autonomous agent uses it.

## Trusted local SQL amendment (2026-11-24)

Notebook SQL Code cells are an explicit local-user action, distinct from autonomous agent execution. The user may submit a single read-only analytical query against a selected registered dataset through a dedicated Rust command. This runs in the desktop host under the user's local privileges, with DuckDB read-only database access, external access and extension autoload disabled, bounded output, and best-effort interruption. These controls protect the app's normal data path but are **not an OS sandbox**. Show that distinction next to Run. The host records exact submitted SQL, the Code block and selected source, pinned representation and engine, status and timing. Code output is bounded and shown under the Code cell; prior executions remain evidence after edits. Autonomous agent execution remains unavailable; trusted Python is specified in the later amendment above. Stronger isolation remains a separate gate for agent-supplied code, not a claim of this trusted path.

## Context

Notebook Code cells store Python or SQL source. Result cells reference completed application-defined executions and can replay them against pinned representations. The current Rust host runs typed filters, sorts and aggregations through embedded DuckDB with bounded results and best-effort interruption. It has no general SQL endpoint or Python runtime. [ADR 0005](0005-dataset-sql-boundary.md), [ADR 0008](0008-python-execution.md) and [ADR 0009](0009-storage-ipc-recovery.md) remain proposed. The [worker fencing spike](../WORKER_FENCING_FEASIBILITY_REPORT.md) verified direct job members on one Windows build and did not establish containment of all descendants.

## Proposed decision

Keep execution policy in the Rust host. Expose a small Notebook interface for submitting an approved operation, observing its status and outputs, and cancelling by execution ID. The host resolves registered representation IDs and owns authorization, quotas, execution records and artifact publication. Use existing analytics directly for the first slice. The trusted Python amendment above uses an existing Jupyter kernel; autonomous execution still requires the separate isolation proof.

A **cell** is editable authored content. An **execution** refers to an immutable submission, including the saved cell revision or exact submitted source, operation/template version and parameters, pinned input representations and fingerprints, runtime and environment versions, limits, times and terminal status. Record bounded output references and hashes when committed. A **result** references that execution. Label replay separately from stored output. Rerunning creates a new execution. Editing a cell or refreshing a source leaves prior evidence intact. Pinning inputs and environments supports replay without promising deterministic output. If persistent sessions are later justified, make restart and state loss visible, record session generation and execution order, and require a clean ordered rerun for reproducibility. Hard cancellation discards the session.

## Implementation sequence and gates

1. **Typed Notebook operations.** Reuse Rust/DuckDB and the Result flow. Let users run existing operations against registered data and insert the resulting execution reference. Show run status and cancellation only where supported. Keep Code as editable source. Verify bounded output, original source immutability, cancellation/status races and provenance across edits and restarts.
2. **Windows isolation proof.** Prototype AppContainer or an equivalent enforceable boundary with explicit ACLs, no network capabilities, a minimal environment and handle allowlist. Broker read-only pinned data and give the worker only quota-bounded scratch space. Keep project stores and publication host-owned. Attach before resume to a non-breakaway Job Object with kill-on-close and CPU, memory and process limits. Enforce wall time, disk, output bytes/rows and concurrency separately. Prove access denial and cleanup across supported Windows builds, including reparse points, credentials, network, child/brokered process paths, stale responses, host crash and restart. Fail closed if setup fails.
