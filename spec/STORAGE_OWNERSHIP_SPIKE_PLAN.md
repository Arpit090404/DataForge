# Storage ownership boundary — Windows proof plan

**Status:** Prepared experiment; **not executed**. No passing result is claimed. Do not begin Milestone 1 until the selected boundary and supported Windows matrix pass review.

## Harness and fixtures

Create a separate disposable `experiments/storage-ownership/` harness; do not modify or reuse the evidence in the IPC/storage or worker-fencing experiments. Use a minimal host controller and a Python worker with pinned experiment-only dependencies. The host owns a synthetic SQLite journal, DuckDB file, private staging/artifact directories, and a stable project ownership handle. The worker receives only brokered synthetic input and IPC output. Launch it under the proposed AppContainer security context; if that cannot run Python/DuckDB on a target configuration, record the failure and separately evaluate a restricted-token/ACL variant. Keep every test under a uniquely created temporary local project. Record OS build/edition/architecture, filesystem, Python/DuckDB/runtime versions, token SIDs/capabilities, ACLs, process and creation identities, handle access masks, timestamps, operation phases, file IDs/hashes, DuckDB relation inventory, and SQLite state. Redact real user paths and use no real data.

The out-of-job attacker fixture must be an **actual surviving process**, preferably launched by the worker through `Win32_Process.Create` where permitted, with a fallback explicitly marked as an injected same-token process outside the Job. Merely observing a failed broker call is not proof that an escaped worker lacks write rights. A test must open/retain handles *before* host death when possible and attempt writes/rename/replace *after* death. The harness must terminate and wait for all test-created processes in a `finally` path; if cleanup cannot establish their identity, stop tests and report manual cleanup without deleting user files.

## Exact test sequence

| ID | Fault / adversary | Required observation and pass condition |
| --- | --- | --- |
| 1 | Normal host/worker run | Host alone opens SQLite/DuckDB/artifacts for write; worker token, process tree, and inherited-handle inventory show no authoritative writable handle; one complete synthetic result is committed and hashed. |
| 2 | Out-of-job survivor | Launch and identify a process outside the Job while host runs, crash host, keep survivor alive, and try direct write/open/rename/delete of SQLite, DuckDB/WAL, artifact, staging parent, and managed-source path. Every authoritative mutation must be denied by the OS while the survivor lives; verify hashes and file IDs. A failed launch is inconclusive. |
| 3 | Retained handle | Before crash, worker/escape attempts to retain a writable handle to each authority class; no such handle may be obtained. If a handle is deliberately injected, show whether it defeats ACLs and treat that configuration as failure; verify production launch never passes it. Test delayed/buffered writes and child handle inheritance. |
| 4 | Live survivor plus recovery | Start replacement host while survivor writes scratch and repeatedly attempts authority writes. Recovery may run after exclusive project ownership is acquired **only if** every authority-write attempt remains denied; any uncertainty blocks recovery. Verify no mutation/reconciliation overlap in repeated races. |
| 5 | Promoted artifact attack | Commit and hash an artifact, then attempt overwrite, append, rename, replace, hard-link and reparse-point substitution from worker and escaped process. All worker mutations must fail; host detects any unexpected identity/hash change and does not return it as valid evidence. |
| 6 | Crash at every promotion barrier | Kill host after journal prepare, after each received chunk, after DuckDB commit, after private-file flush, after file rename, and before/during/after SQLite terminal commit. On restart, never publish a partial stream or orphan solely because bytes/table exist; preserve earlier completed execution and quarantine only proven unreferenced outputs. |
| 7 | Repeated recovery and retry | Reconcile twice and compare stable SQLite state, DuckDB inventory, artifact hashes, quarantine records; retry with a new attempt ID only after prior state is known. Re-deliver stale/duplicate chunks and success messages; no duplicate publication or terminal-state change. |
| 8 | Concurrent hosts | Start two hosts against the same project before and during crash/restart. Exactly one may hold the project writer ownership handle; the loser blocks or opens read-only. No simultaneous DuckDB writes or journal reconciliation. Test lock release after abrupt death without a fixed delay. |
| 9 | Disk full / partial I/O | Inject short writes and actual quota/volume-full conditions for private staging, DuckDB and SQLite final commit, then recover. Record which failures are simulated versus actual. No incomplete output may be referenced as succeeded; previous completed hashes remain unchanged. |
| 10 | Parser and source escape | Feed malformed synthetic CSV/Parquet/JSON/XLSX fixtures and attempt unrelated-user-file reads, network calls, privilege/token regain, WMI/COM/scheduled-task child creation, and scratch-to-project reparse/hard-link swaps. Distinguish denied calls from untested APIs. Any path to a project-writable identity fails the boundary. |

For each test, capture state *before* fault, while the survivor is active, at recovery admission, and after two reconciliations. Verify SQLite journal/terminal references, DuckDB table schema/count/content hash, artifact bytes/hash/file ID, original source hash, and absence of unintended project mutations. Use operation IDs and signed-off expected state in test fixtures; do not infer success from a worker response alone. Keep raw logs and a machine-readable result file, with each case marked pass/fail/inconclusive. Repeat crash/restart/survivor cases enough to expose timing races, recording the count rather than presenting a small sample as reliability proof.

## Acceptance and stop conditions

The design is eligible for ADR 0009 acceptance only if all authority classes deny surviving worker/escaped-process writes, host-only handles cannot leak, exclusive project ownership holds, partial output is never published, reconciliation is repeatable, completed evidence survives, and the results pass on **every Windows/filesystem configuration DataForge chooses to support**. An inaccessible or ambiguous token/ACL/handle state blocks recovery. A failed escaped-process launch, missing actual disk-full test, untested configuration, or a model-only stale-message test is inconclusive, not a pass. A demonstrated out-of-job writer under the host user identity fails the proposed AppContainer/restricted-token construction and requires the separate-principal fallback or a narrower product support decision.

This plan is documentation only. The existing 18/18 worker-fencing and 15/15 plus 22/22 IPC/storage results remain evidence for their original, narrower experiments; they are not transferred to this architecture.
