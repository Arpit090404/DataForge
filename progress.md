## Trusted local Notebook SQL (2026-11-24)

SQL Code cells now have an explicit Run/Cancel control and a ready registered-source picker. The saved SQL runs through a dedicated Rust command: the host resolves and materializes the selected CSV, then a short-lived child of the desktop executable opens the analytical DuckDB database read-only and returns a bounded result beneath the cell. The host records exact SQL, Code block ID, source fingerprint, pinned representation and DuckDB version, timestamps, status, row count or error in a version-2 execution. Editing and rerunning creates another execution. Typed analysis and Result cells retain their existing paths; Python and automatic agent execution remain disabled. The UI states that trusted SQL runs locally with the user's privileges and that DuckDB settings are not an OS sandbox.

The child process is necessary because a malformed SELECT was observed to abort the in-process DuckDB/Rust boundary. The parent kills the direct child on Cancel or the 30-second deadline and rejects late output; the host can run another query after a child crash or cancellation. SQL is limited to one `SELECT`-leading statement of 8 KiB, with 200 output rows, 128 columns and 1 MiB of cell values. The selected source is recorded context, not complete lineage: other tables in the project analytical database may be addressable. The child has the user's OS rights; hard CPU, memory, scratch, process-tree and filesystem/network isolation are not claimed. SQL output is session-only and cannot be replayed after reopening; metadata and exact SQL persist. The autonomous SQL security gate remains no-go.
